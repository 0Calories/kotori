# Deploying Kotori

What is left to do, by hand, to finish the deployment. How production runs once it is up — environment, operations, the auth model, CI — is in `operations.md`.

State as checked on 2026-10-23: the API and worker are deployed to Fly (`kotori.fly.dev`) with all six secrets set and the dictionary seeded; the web app is live on Vercel (`kotori-mocha.vercel.app`) and built against the Fly API; both origins are Managed Auth trusted domains on the production branch; CI is green on `main`. Production has two accounts, one approved, and no admin.

## 1. Finishing the deployment

In order. Each step is independent of the ones after it unless it says otherwise.

1. **Start the machines.** Both Fly machines are stopped. The API starts itself on the first request, the worker does not, and nothing enriches or emails approvals until it runs:

   ```sh
   fly machine start 683e27df037ee8 87472d4f675508
   ```

2. **Let the web app sign in.** The API's CORS allowlist is empty, so the browser's credentialed requests are refused. In `fly.toml` under `[env]`, uncomment and set the line, commit, deploy:

   ```toml
   KOTORI_WEB_ORIGINS = 'https://kotori-mocha.vercel.app'
   ```

3. **Turn on email.** Managed Auth's webhook is disabled on production, so verification and reset codes are only written to the API log. Point it at the API (events are space-separated; the 10 s timeout leaves Resend's retries room under Neon's 15 s cap):

   ```sh
   neon neon-auth config webhook update --branch production --enabled \
     --url https://kotori.fly.dev/webhooks/neon-auth --enabled-events send.otp send.magic_link --timeout 10
   ```

   `RESEND_API_KEY` is set. `KOTORI_EMAIL_FROM` is not, so mail goes out from Resend's `onboarding@resend.dev`, which only delivers to the Resend account's own address — set it to a verified domain (`fly secrets set KOTORI_EMAIL_FROM='Kotori <hello@…>'`) before anyone else signs up. Then sign up on the web app with a real address and confirm the code arrives; `fly logs --process-group api` says `Sent the email-verification email` or names the reason it didn't.

4. **Close localhost on production auth.** It is still allowed, which means a dev server on anyone's laptop can talk to the production auth endpoint:

   ```sh
   neon neon-auth domain allow-localhost disable --branch production
   ```

5. **Make yourself admin** (needs the worker machine running, from step 1):

   ```sh
   fly ssh console --process-group worker -C "node apps/worker/dist/main.js admin you@example.com"
   ```

6. **Deploy from CI.** The Fly deploy job currently skips. Create a deploy token and set it as the repository secret `FLY_API_TOKEN`, then the repository variable `FLY_DEPLOY=true`:

   ```sh
   fly tokens create deploy -x 8760h
   ```

   `VERCEL_ORG_ID` and `VERCEL_PROJECT_ID` are set as repository variables but no workflow reads them; Vercel deploys through its own Git integration. Remove them, or keep them for a CI-driven Vercel deploy if that is the plan.

7. **Decide about Vercel previews.** Each preview deployment gets its own origin, which the allowlist rejects, so previews load but cannot sign in or call the API. Either leave them that way, turn preview builds off in the project's Git settings, or wait for preview backends (`operations.md`, Follow-ups).

8. **Before inviting anyone.** Send test emails to Gmail, Outlook and iCloud addresses once the Resend domain has SPF and DKIM. Use production-only API keys at Anthropic, ElevenLabs, TypeSafe and Resend, each with a hard spend cap. If the API or web app move to custom domains, every place that names an origin changes with them: `KOTORI_WEB_ORIGINS`, the Managed Auth trusted domains, `EXPO_PUBLIC_API_URL` on Vercel (redeploy), and `fly certs add` for the API.

## 2. Native builds (item 4)

Nothing exists yet: no `eas.json`, no EAS project id in `app.json`, no native project directories (they are generated by `expo prebuild` and gitignored), and the app has never run against an HTTPS API on a device. The parts only you can do:

1. **Accounts.** An Apple Developer Program membership (TestFlight and the App Store), a Google Play Console account, and an Expo account for EAS.

2. **Link the project.** From `apps/app`, signed in to Expo:

   ```sh
   npx eas-cli login
   npx eas-cli init               # creates the EAS project and writes extra.eas.projectId into app.json
   npx eas-cli build:configure    # writes eas.json with build profiles
   ```

   Commit both files. Everything after this an agent can do; the two commands above need your Expo login.

3. **Give the builds the API URL.** `EXPO_PUBLIC_API_URL` is inlined at build time for native exactly as for web, and unset it falls back to the Metro host, which a device build cannot reach. Set it to `https://kotori.fly.dev` for the production profile (and any preview profile) either as an EAS environment variable or under `env` in the profile in `eas.json`.

4. **Signing.** Let EAS manage credentials. The first iOS build asks for your Apple ID and two-factor code to create the distribution certificate and provisioning profile; the first Android build generates and stores a keystore. Keep that keystore: Play signs with its own key, but uploads must be signed with this one.

5. **Build and ship to testers.**

   ```sh
   npx eas-cli build --platform ios --profile production && npx eas-cli submit --platform ios
   npx eas-cli build --platform android --profile production      # upload the .aab to an internal testing track
   ```

6. **Verify on a device against production** (steps 2 and 3 of section 1 first, or sign-in and codes won't work): sign up and confirm the code; see the pending screen; approve yourself with the CLI and watch it move on; kill and relaunch the app and still be signed in; sign out; play audio; change the password; delete the account.

7. **Store listing.** App Store Connect and Play Console both want screenshots at specific sizes (the ones in `docs/screenshots` are illustrative, not store-sized), a privacy policy URL, a support URL, data-collection declarations (email address and study activity, tied to the account), and an age rating. App review will need an account that already works: sign one up and approve it with `kotori approve`, and give them the credentials. Account deletion in Settings covers Apple's requirement; email-and-password is the only sign-in, so Sign in with Apple is not required.

## 3. For the agent picking up item 4

Read this before touching the app's native side.

**Where things stand.** `apps/app` is Expo SDK 57 on React Native 0.86 with the new architecture on, `expo-router`, and bundle identifier / package `app.kotori` on both platforms (`app.json`). There is no `eas.json`, no `extra.eas.projectId`, and no `expo-dev-client`. `apps/app/ios` and `apps/app/android` are gitignored prebuild output. The owner has to run `eas init` and `eas build:configure` themselves (Expo login); after that, profile contents, `app.json` changes and any CI wiring are yours.

**Build-time environment.** Expo inlines `EXPO_PUBLIC_*` at build time. `apps/app/src/api/config.ts` falls back to the Metro host on port 4000 when `EXPO_PUBLIC_API_URL` is unset, so a build without it compiles cleanly and then fails on the device. One observation from this session, local only: after a build, Metro's transform cache served a bundle with the *previous* inlined `EXPO_PUBLIC_API_URL` when the value changed. EAS builds run on fresh machines, so it probably does not apply there; it may to local `expo run:ios` / `run:android` builds, where `--clear` is the remedy.

**The development sign-in must not reach release builds.** `apps/app/src/auth/dev.ts` signs the app in as `dev@kotori.test` when `__DEV__` is true (off with `EXPO_PUBLIC_DEV_SIGN_IN=off`). The credentials are duplicated in `apps/worker/src/commands/accounts.ts` (`kotori dev-account` creates the account) on purpose: a shared module survived in the release bundle, whereas the app-local copy folds away with the `__DEV__` branch. That was verified on the web export; verify it on the first native release build too. Nothing in the app's Vitest config defines `__DEV__`, so a test that imports `dev.ts` would throw until it does.

**How auth works on a device, and what has never been tested.** The long-lived credential is Managed Better Auth's session cookie (`__Secure-neonauth.session_token`, HttpOnly). Native apps read it from `Set-Cookie` on the proxied sign-in/sign-up responses, keep only the `*.session_token` cookie in the Keychain/Keystore via `expo-secure-store` (`apps/app/src/auth/transport.ts`, `cookies.ts`, `session/storage.ts`), and send it back as a `Cookie` header to `/api/auth/*` only, with `credentials: "omit"` so the OS cookie jar plays no part. From it the app mints 15-minute JWTs at `GET /api/auth/token` (`tokens.ts`) and sends those as `Authorization: Bearer` to everything else. A 401 from `/token`, or the API refusing a freshly minted JWT, signs the app out; a 5xx keeps the credentials. `cookies.ts` splits the comma-joined `Set-Cookie` header React Native produces, and `test/cookies.test.ts` covers it. All of that has only ever run against a local HTTP API. The first thing to establish on a real device over HTTPS is whether the `Set-Cookie` header is visible to `fetch` at all on iOS and Android with `credentials: "omit"` — React Native's networking layers differ from browsers here. Native requests carry no `Origin`; the API's proxy substitutes its own public origin, and `https://kotori.fly.dev` is already a trusted domain, so that gate is covered. `operations.md` has the full model.

**Also built this session but not verified against Managed Auth:** `POST /change-password` (core Better Auth, not a plugin, so it should be exposed; the app re-mints its JWT after it) and the forgot-password flow (`/email-otp/send-verification-otp` with `type: "forget-password"`, then `/email-otp/reset-password`; the webhook already handles that code type). Account deletion (`DELETE /account/me`) was exercised end to end over HTTP. Email delivery from production was not — the webhook was disabled when this was written.

**`app.json` details.** `NSAppTransportSecurity.NSAllowsLocalNetworking` is on for iOS so development builds can reach a dev server on the LAN; it does not weaken HTTPS to the API and Apple does not reject it, so leave it unless there is a reason not to. `experiments.typedRoutes` is on. `knip` reports `expo-updates` as an unlisted dependency from `app.json`; the cause was not investigated and OTA updates are not configured.

**Repository conventions that bit this session.** `.node-version` is 24.22.1 and `engines.node` is `>=24`; a shell on Node 22 runs the servers but is not what CI uses. The API and worker `dev` scripts are `tsx watch --clear-screen=false -C @kotori/source …` and the flag order matters: tsx stops parsing its own flags at the first unknown one, so `-C` first hands `--clear-screen` to node, which rejects it and nothing listens. `pnpm lint` has a baseline of 25 warnings and `pnpm knip` a baseline of failures (an unused `neon.ts`, a few dependency entries); neither is in CI, so compare against the baseline rather than expecting zero. `oxfmt` formats Markdown too; run `pnpm format` before committing docs.
