# Data model rebuild on Drizzle 1.0

> Temporary working document for the rebuild of `packages/db`. Tracks the phases agreed
> on 2026-10-27 and the decisions behind them. Delete it at cutover, once
> `docs/operations.md` and the README describe the finished state.

## Why

The first data layer was hand-written SQL behind Effect repositories: fine for the MVP,
but every table's columns lived in four places (migration, row schema, column list,
encoder), migrations were authored by hand, and nothing inside a SQL string was
type-checked. Kotori is pre-beta with no users, so the model is rebuilt from scratch on
Drizzle 1.0 (release candidate), whose Effect driver runs on the `@effect/sql-pg` and
`@effect/sql-pglite` clients already in use. The Drizzle schema in `packages/db/src/schema`
becomes the single source of truth: migrations, row and insert types, and Effect Schemas
all derive from it.

## Decisions

- **Drizzle 1.0.0-rc.5**, pinned exactly in the pnpm catalog; bump `drizzle-orm` and
  `drizzle-kit` together.
- **Repository interfaces stay the boundary.** `apps/*` and `@kotori/domain` never import
  Drizzle; the six repositories are rewritten against the query builder behind the same
  kind of Effect services.
- **Timestamps are `timestamptz`.** The SRS code keeps working in millisecond numbers;
  repositories convert at the boundary.
- **Real foreign keys everywhere inside a domain**, including enrichment → `entries` with
  cascading deletes. The JMDict seeder therefore upserts instead of truncating.
- **Identifiers are `uuid`**, generated by Postgres, for the study tables. The append-only
  logs (`review_logs`, `coach_usage`) keep identity integers: nothing outside refers to them.
- **Postgres-native types** replace JSON-in-text: enums for kind, status, queue, template
  and rating; arrays for tags and parts of speech; `jsonb` with `$type` for structured
  content.
- **Postgres 18 locally** (`compose.yaml`), the same major as Neon. PGlite stays on
  whatever `@effect/sql-pglite` ships.
- **`neon_auth` stays Neon's.** Its tables are declared read-only in `src/neonAuth.ts`,
  which `drizzle.config.ts` does not list under `schema`, so drizzle-kit never sees them.
  Verified in phase 1: `schemaFilter` gates introspect and push only, and a `pgSchema`
  reachable from the diffed schema file produced a `CREATE SCHEMA "neon_auth"` migration.
  No foreign key from `users` into it.
- **Column naming** is applied per table with `snakeCase.table` from
  `drizzle-orm/pg-core/casing` (Drizzle 1.0 removed the driver-level `casing` option).
- **Migrations run as a deploy step, never at startup.** `kotori migrate` is Fly's
  `release_command` and a step in `pnpm dev:setup`. This removes the API/worker startup
  race the old migrator had to lock around.

## After the cutover

The repositories are a stopgap. The agreed end state is a `packages/services` application
layer that owns all data access directly through Drizzle, with the provider packages no
longer persisting anything. That restructuring is specified in
docs/services-restructuring.md and starts once phase 5 is done.

## Phases

### Phase 1 — Foundation ✅ (2026-10-27)

- `drizzle-orm` and `drizzle-kit` 1.0.0-rc.5 in the catalog and `packages/db`.
- `Database` service (`packages/db/src/Database.ts`): the Drizzle instance over the Effect
  `PgClient`, typed by the drivers' common base so Postgres and PGlite share it.
  `DatabaseLive` no longer migrates.
- `migrateDatabase` (`packages/db/src/Migrate.ts`): driver-neutral Effect that applies
  `packages/db/migrations`. Exposed as `kotori migrate` in the worker CLI.
- `drizzle.config.ts`; `pnpm --filter @kotori/db generate` and `check` scripts.
  `src/schema/index.ts` holds only the snake_case table constructor for now.
- `packages/db/test/database.test.ts` runs the Drizzle service and the migrator on PGlite.
- Deploy wiring: Fly `release_command`, Dockerfile copies `packages/db/migrations`,
  `pnpm dev:setup` runs `kotori migrate` before seeding, Compose on Postgres 18.
- `DatabaseMemory` provides `Database` over PGlite **and still runs the legacy SQL
  migrations** so the current repositories and their tests keep working until phase 3.

The README's package description and setup notes are updated at cutover (phase 5).

### Phase 2 — Schema design ✅ (2026-10-27)

- `src/schema/`: `columns.ts` (snake_case table constructor, `timestamptz`, `createdAt`,
  the `text COLLATE "C"` and `tsvector` custom types), `dictionary.ts`, `enrichment.ts`
  (including `jobs`), `study.ts` (including the coach tables), `relations.ts`, `tables.ts`,
  `index.ts`. `src/neonAuth.ts` declares `neon_auth.user` and `neon_auth.session`
  read-only, outside the kit's `schema` path.
- Migration `20261027175222_initial` generated; `generate` is a no-op afterwards.
- `Database` is typed with `typeof relations`; `DatabaseMemory` migrates PGlite from the
  migrations folder and no longer runs the legacy SQL migrations.
- `test/schema.test.ts` checks the Postgres-level behaviour on PGlite: generated
  full-text column, C collation on `forms.text`, cascades, relational reads.

What changed from the old model, beyond types: `glosses` carries JMDict's gloss `type`
and `senses` no longer duplicates glosses as JSON (gloss counts come from the table);
`coach_usage` has a key and cascades from `users`; `jobs.run_after` is a timestamp
defaulting to now; `review_logs.delay` became `delay_ms` (still `bigint`: a long review
interval overflows `integer` milliseconds); `notes.entry_id` is a real key
with `ON DELETE SET NULL`; enrichment references `senses` by `(entry_id, position)`.

Learned: Drizzle 1.0's relations need explicit `from`/`to` on every side unless the
reverse is declared; Postgres enums sort by declaration order, so `form_kind` is declared
kanji-first and ordered ascending; `db.execute` is untyped on the shared base type, so raw
SQL in repositories should go through `db.select` with `sql<T>` fragments.

### Phase 3 — Repositories ✅ (2026-10-27)

- The six repositories are rewritten on the query builder with their interfaces kept,
  so `apps/*` changed in three places only: the coach cache stores and returns the
  encoded value itself (`jsonb`) instead of a JSON string, the review log field is
  `delayMs`, and the API test counts notes through `StudyRepo.noteCount`.
- Row types (`UserRow`, `CardRow`, `NoteRow`, `AudioRow`, `Job`, …) are plain
  interfaces in millisecond epochs; `rows.ts` converts to and from `Date` at the
  boundary. No Effect Schema decoding of rows remains: Drizzle types them.
- `packages/tts` `AudioStore` and `packages/auth` `Auth` now query through `Database`
  too (`audio_files`, and the read-only `neon_auth` tables). `Pronouncer` writes the
  `audio` row before the bytes, since `audio_files` references it.
- Deleted: `migrations.ts`, the `int8AsNumber` codec and its test, and the `PgClient`
  name transforms. `DatabaseLive` is now just Drizzle plus the plain `PgClient`.
- `test/repos.test.ts` ported to uuid ids and extended: enrichment (nuance, similar
  words, examples with audio links and replacement), users (ensure, update, cascade on
  delete through coach usage), coach cache freshness, study statistics.
- Full workspace: typecheck, 12 test projects, lint and format all pass.
- Review fixes: the seeder upserts senses instead of deleting them, so reseeding keeps
  enrichment (only senses an entry lost take theirs with them); migration
  `20261027233713_coach_kind_and_delay_bigint` makes `coach_usage.kind` an enum and
  `delay_ms` a `bigint`; the redundant drizzle-kit `casing` option is gone.

Learned: `bytea` travels as a `Buffer` in Drizzle; enum ordering again (cards order by
`template` ascending, recognize before produce); `jobs` now needs real `entries` rows,
which the tests stub.

### Phase 4 — Seeding and enrichment ✅ (2026-10-27)

Point the JMDict seeder (upserting) and the enrichment worker at the new tables. Dictionary
and enrichment are rebuildable, so this is a reseed, not a data migration.

- The seeder (`packages/jmdict`) and the enrichers (`packages/nuance`, `ai`, `tts`) already
  went through the kept repository interfaces, so they needed no changes. Neither did
  `kotori seed`, `enrich` or `status`.
- **Seeding failed on real Postgres.** `@effect/sql-pg` infers parameter types from the
  values and can't bind an empty JS array, and Drizzle's Effect Postgres codecs pass
  `text[]` through as JS arrays (most other array types become literals). Every form
  without tags or sense without misc codes failed. `Database.ts` now gives the driver
  `pgCodecs`, which send `text[]` as array literals; `test/database.test.ts` checks the
  encoding, since PGlite never had the problem. No schema change.
- `migrateDatabase` fails with `LegacySchemaError`, changing nothing, on a database with
  `effect_sql_migrations` and no `drizzle.__drizzle_migrations`. `kotori migrate` prints
  what to do (locally `docker compose down -v`; on Neon reset the branch) and exits 1.
- `compose.yaml` mounts the volume at `/var/lib/postgresql`. Postgres 18 images refuse
  `/var/lib/postgresql/data` even on a fresh volume, so the phase 1 compose file didn't
  start at all. A Postgres 17 volume (main's) still won't start: `pnpm dev:setup` spots
  the image's error in the container log and says to run `docker compose down -v`. It
  never deletes anything itself. The README's setup step says the same.
- The worker's claim/run/settle cycle moved from `commands/work.ts` to `src/JobRunner.ts`.
  `apps/worker` now has tests: queued nuance and examples run into the new tables through
  the real enrichers with fake Jev, Claude and ElevenLabs, examples queue audio, and a
  failed job retries after its delay. `packages/jmdict/test/import.test.ts` seeds twice
  and keeps nuance, examples and queued jobs; a newer release drops only the lost senses'
  enrichment and updates tag labels.
- Verified against a throwaway Postgres 18 in Docker: `dev:setup` stops correctly on a
  Postgres 17 volume and on a legacy schema; from fresh it migrates, seeds 218,969
  entries (~25 s) and creates the dev account; a re-run skips each step. A full reseed
  (~26 s) keeps enrichment and queued jobs, and every entry reads back equal to the
  parsed JMDict. The worker, API and repository test suites also pass when pointed at
  that database through `DatabaseLive` (a one-off run, not part of CI).

Learned: PGlite is more lenient than `@effect/sql-pg` about parameters, so the repository
tests can pass while Postgres fails. Anything that binds a new kind of value needs one
run against real Postgres. Main's Compose file was Postgres 17, not 16. The seeder still
doesn't delete entries a newer JMDict drops (neither did the old one); they stay
searchable until a reset.

### Phase 5 — Cutover

Reset the Neon production branch, `kotori migrate`, reseed, deploy. Update
`docs/operations.md` and the README; delete this document. The two existing accounts keep
their `neon_auth` identity and get fresh profile rows on first request. Local developers
run `docker compose down -v` once for the Postgres 18 volume.

From phase 4: `kotori migrate` refuses an unreset branch (legacy schema) with exit 1, so
Fly's release command fails safely if the reset is skipped. CI still tests on PGlite only,
so smoke-test the deployed API against Neon once after the reseed (sign in, search,
review); the one-off Postgres 18 runs above cover the code paths, not Neon's network or
TLS. `apps/api` `Accounts` still opens its transaction through `SqlClient` directly;
that's fine for now, and the services restructuring removes it.
